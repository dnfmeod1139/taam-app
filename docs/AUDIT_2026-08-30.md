## 이미 막은 것

### 1·2. 역할 자가 승격 (`sql/guard_profile_role.sql`) — 실행 완료

`profiles_update_own` 이 `(auth.uid() = id) OR is_superadmin()` 이라 자기 행을
고칠 수 있었고, **`role` 컬럼이 그 행에 있었다.** 한 줄이면 슈퍼어드민이 됐다.

```sql
update profiles set role = 'super_admin' where id = <내 id>
```

INSERT 쪽도 같았다. `profiles_insert_own` 의 WITH CHECK 가 `(auth.uid() = id)` 뿐이라
행이 없는 새 계정은 가입 직후 `role='super_admin'` 으로 만들 수 있었다.

BEFORE UPDATE 는 조용히 되돌리고, BEFORE INSERT 는 예외를 던진다.
**실제 피해 없음** — 대조 결과 슈퍼어드민은 아는 계정 하나뿐이었다.

### 4. 예치금 (`sql/deposit_server_side.sql`) — ①②③ 실행, ④ 대기

잔액도 자기 행에 있었다. `taam_apply_deposit_delta` 로 옮겼고(앱은 `-w` 부터
델타만 보낸다), 직접 쓰기를 막는 ④ 는 **배포 확인 뒤에** 올린다.

`sql/_deposit_audit.sql` 대조 결과 **기록 없이 잔액이 는 계정은 없었다.**
어긋난 두 건은 사장님 계정의 천원 단위 테스트 흔적이다.

## 오늘 새로 찾은 것

### 5. `tickets` — 자기 예약을 고쳐 쓸 수 있다 🆕

`tickets_update_own` 이 같은 모양이라 이런 것이 통했다.

```sql
update tickets set party_size = 8    where purchase_id = '내 것'    -- 좌석을 더 가져간다
update tickets set status = 'active' where purchase_id = '내 취소건' -- 취소를 되살린다
update tickets set price = 0         where purchase_id = '내 것'    -- 매출 기록을 지운다
```

돈이 그 자리에서 빠져나가진 않는다. 대신 **좌석이 실제로 줄고**, 매출·정산이
어긋나고, 취소된 예약이 되살아난다. 예치금보다 조용해서 더 늦게 들킨다.

**예치금과 달리 지금 바로 막을 수 있다.** 앱이 회원 세션으로 하는 UPDATE 는
둘뿐이기 때문이다 — ① 결제 확정(`hold`→`active` + price) ② 취소(status + extra_data).
그 둘만 허용하면 앱이 안 멈춘다.

→ `sql/guard_tickets.sql` · 로컬 12가지 검증 완료 · **배포 없이 지금 실행 가능**

### 6. `send-push` — 회원 누구나 전 회원에게 푸시를 쏠 수 있다 🆕

`send-push` 는 호출자의 `user_id` 를 뽑기는 하는데 **그걸로 아무것도 막지 않는다.**
`to` 를 그대로 믿는다.

```js
supabase.functions.invoke('send-push', {
  body: { to: 'all', payload: { title: '아무 말', body: '전 회원에게' } }
})
```

로그인한 회원이면 누구나 된다. `to:'role:super_admin'` 으로 운영진에게만 쏘거나,
`to:'uid:<남의 id>'` 로 특정 회원을 괴롭힐 수도 있다.

**처음엔 「role: 도 어드민만」으로 짰다가 되돌렸다.** 회원이 `role:` 을 정당하게
쓰는 자리가 둘 있었다.

- `confirmTimeChange()` — 고객이 시간 변경을 확인하면 슈퍼어드민에게 알린다
- 매진 경합 자동 환불 — 회원 세션에서 환불이 나면 슈퍼어드민에게 알린다

막았으면 이 둘이 **조용히 죽었을 것이다.** 위로 올라가는 알림(운영진에게)과
아래로 내려가는 알림(전 회원·남의 기기)은 위험이 다르다. 그래서 이렇게 나눈다.

| `to` | 누가 쓸 수 있나 |
|---|---|
| `user` · `uid:<본인 id>` | 누구나 — 본인에게 |
| `role:admin` · `role:superadmin` · `role:super_admin` | 로그인한 회원 — **위로 올려보내기** |
| `all` · `topic:` · `role:user` · `uid:<남의 id>` | **어드민만** |
| (service_role 키로 부르는 서버 간 호출) | 그대로 통과 — `toss-confirm` 등이 쓴다 |

`role:user` 를 「위로」에 넣지 않은 것이 요점이다 — 그건 이름만 role 이지 사실상
전 회원 브로드캐스트다.

→ `supabase/functions/send-push/index.ts` · **대시보드 붙여넣기 필요**

## 아직 남은 것 (설계가 필요하다)

### 7. 재구매 제한이 클라이언트에만 있다 🟠

`checkRepurchaseLimit()` 은 브라우저 메모리의 `purchaseHistory` 를 뒤진다.
서버에는 이 규칙이 **아예 없다.** 두 가지가 걸린다.

- 앱을 거치지 않으면 그냥 통과한다
- 앱을 거쳐도, `purchaseHistory` 가 덜 실려 있으면 **조용히 안 걸린다**
  (오늘 아침 구자호 회원 건이 연도 문제였지만, 이 구조 자체도 같은 위험을 갖는다)

**고치는 법**: 좌석 트리거와 같은 자리에서 막는다. `tickets` INSERT 시
같은 `user_id` + 같은 `restaurant_id` 의 살아 있는 예약을 찾아 방문일 간격이
`restaurants.repurchase_day` 안이면 거부. 면제(슈퍼어드민·심사 계정)도 서버에서 본다.
→ 앱 수정 없이 SQL 만으로 가능하다. 다만 **정상 구매를 막을 위험**이 있어
   먼저 「막혔을 것」을 세어 보는 조회부터 만든다.

### 8. 결제 없이 예약 행을 만들 수 있다 🟡

`tickets_insert_own` 이 `(auth.uid() = user_id)` 라 회원이 자기 예약 행을
직접 넣을 수 있다. 다만 **좌석 트리거가 이미 서버에서 좌석을 지킨다**
(`TICKET_SOLD_OUT` · `SLOT_SOLD_OUT` · `SOLO_LIMIT` · `FRAGMENT_BLOCKED`).
없는 좌석을 만들어 낼 수는 없고, **「돈 안 내고 남은 좌석을 차지」는 가능**하다.

구매 흐름을 서버 RPC 로 옮겨야 제대로 막힌다 — 예치금과 같은 순서다.
UPDATE(5번)를 먼저 막아 두고, INSERT 는 그다음.

### 9. `deposit_transactions` 가짜 기록 🟢

자기 이름으로 거래기록을 넣을 수 있다. **잔액은 안 움직인다** — 그 테이블에
트리거가 하나도 없는 것을 확인했다(로컬에서 9,999,999원짜리 가짜 기록을
넣어도 잔액 그대로). 내역 화면만 지저분해진다. 급하지 않다.

### 10. `membership_tier` · `membership_expires_at` 🟡

자기 행이라 M 등급으로 올리거나 만료일을 미룰 수 있다. 가입 흐름이 초대코드
등급을 여기에 쓰고 있어 같이 막으면 가입이 깨진다. 서버로 옮긴 뒤 막는다.

### 11. 중복 sync 트리거 🟢

`trg_sync_deposit_balance` 와 `trg_taam_sync_deposit_balance` 가 **같은 일**을 한다
(`deposit_balance = 멤버십 + 일반`). 둘 중 하나는 지워도 된다. 지금은 무해하다.

## 확인했고 문제 없던 것

- **RLS SELECT** — 모든 테이블이 `자기 행 or 슈퍼어드민`. 어드민 화면이 잘못
  열려도 **남의 데이터는 안 보인다.** 오늘 `ripe0315` 건이 이것 덕에 정보 유출이
  아니었다.
- **좌석 동시성** — 서버 트리거가 지킨다. 두 사람이 동시에 마지막 자리를 눌러도
  하나만 통과한다.
- **`taam-sms-hook` 의 `verify_jwt = false`** — Auth 훅은 JWT 대신 Standard
  Webhooks 서명을 보낸다. 서명 검증 + 5분 창으로 스스로를 지키므로 정상이다.
- **단일 기기 로그인** — 3겹(Realtime·워치독·서버 세션 폐기)이 다 살아 있다.
- **예치금 대조** — 실제 조작 흔적 없음.

## 이 감사에서 배운 것

**같은 모양의 구멍이 네 군데였다.** `profiles.role` · 예치금 잔액 · `tickets` ·

> 답이 「돈·권한·좌석이 움직인다」면, RLS 로는 부족하고 **트리거나 RPC 가 필요하다.**
