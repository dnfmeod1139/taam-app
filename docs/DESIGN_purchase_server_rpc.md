## 지금 상태 (코드를 실측했다)

「구매 흐름을 통째로 서버로 옮긴다」로 적어 뒀는데, 열어 보니 **이미 절반은
서버에 있었다.** 옮길 것이 생각보다 적다.

| 단계 | 지금 누가 하나 | 안전한가 |
|---|---|---|
| 좌석 홀드 INSERT (`status='hold'`, `price=0`) | 앱 | 무해 — 돈이 안 걸림, 5분 만료 |
| **카드 결제 확정** (`hold→active` + price) | **서버** `toss-confirm` | ✅ 이미 안전 |
| **예치금 결제 확정** | **앱** | ⚠ 여기가 구멍 |
| 예치금 차감 | **서버 RPC** `taam_apply_deposit_delta` | ✅ 어제 옮김 |
| 로컬 백업 동기화 INSERT (`status='active'`) | 앱 | 🔴 **가장 큰 구멍** |

`toss-confirm` 은 service_role 로 `hold→active` 를 쓰고 금액도 서버가 정한다.
**카드로 사는 길은 이미 막혀 있다.** 남은 것은 예치금 경로와 동기화 경로뿐이다.

## 무엇이 뚫리나

### 🔴 ① 동기화 경로 — `savePurchase()`

브라우저 메모리의 `purchaseHistory` 를 DB `tickets` 와 비교해서, **DB 에 없는
것을 앱이 INSERT 한다.** `status:'active'` 로.

```js
status: h.status === 'upcoming' ? 'active' : ...
```

`purchaseHistory` 는 로컬 백업에서도 복원된다. 즉 **회원이 자기 브라우저 저장소에
가짜 구매를 하나 적어 두면, 앱이 그걸 「DB 에 없네」 하고 올려 준다.** 돈이 한 푼도
안 움직이는데 확정 예약이 생긴다.

이 경로는 원래 「복구」용이다. 그런데 오늘 아침 겪었듯이 **고치기보다 망가뜨린
전례가 있다** — 연도 없는 옛 형식(`'1.23'`)을 그대로 다시 넣어서, 재구매 제한과
감사가 판정할 수 없는 행을 계속 만들어 냈다.

### ⚠ ② 예치금 확정 — 금액을 앱이 정한다

```js
var paid = (window._tdPayAmount > 0) ? window._tdPayAmount : (meal+agency+wine)*pax;
...
.update({ status: 'active', price: paid, ... })
```

`paid` 가 클라이언트 값이다. **앱을 거치지 않으면 아무 금액이나 쓸 수 있다.**
예치금 차감은 어제 서버 RPC 로 옮겼지만, **차감액과 티켓 금액이 서로를 검증하지
않는다** — 1원만 차감하고 `price` 를 90만원으로 적을 수 있다.

### 🟡 ③ 좌석 홀드 INSERT

`price=0`, `status='hold'`, 5분 뒤 자동 만료라 **그 자체로는 무해**하다.
문제는 회원이 같은 테이블에 `status:'active'` 로 넣을 수 있다는 것인데,
그건 ①을 막고 나서 INSERT 를 잠그면 같이 닫힌다.

## 설계 — 네 단계, 각각 따로 배포하고 따로 되돌릴 수 있게

위험이 낮고 값이 큰 것부터. **각 단계가 끝날 때마다 앱이 정상인지 확인하고
다음으로 간다.** 한 번에 다 하지 않는다 — 금전 코드다.

### 1단계 — 동기화 경로를 「올리기」에서 「내려받기」로 (위험 낮음 · 값 큼)

DB 가 진실이다. 앱 메모리가 DB 를 고치는 방향을 **없앤다.**

- `savePurchase()` 의 **INSERT 를 제거**한다
- DB 에 없는 구매가 메모리에 있으면 → **INSERT 대신 슈퍼어드민에게 알린다**
  (`notifications` 에 `sync_missing` 한 줄). 조용히 사라지지 않게

> **왜 알림인가**: 정말로 DB 에 못 올라간 구매가 있다면 그건 **결제 쪽 버그**다.
> 앱이 몰래 메워 버리면 그 버그를 영영 못 찾는다. 오늘 아침 연도 사고가
> 정확히 그렇게 쌓인 것이다.

- 되돌리기: 그 블록만 복원 (앱 배포 한 번)
- 확인: 구매 → 취소 → 앱 재시작에서 내역이 그대로 보이는가

### 2단계 — 예치금 확정을 서버 RPC 로 (위험 중간 · 값 큼)

```
taam_purchase_confirm_deposit(p_purchase_id text, p_expect_amount bigint)
```

한 트랜잭션 안에서 전부 한다.

1. `purchase_id` 의 홀드를 잠그고(`for update`) 읽는다
2. **내 것인가 · `status='hold'` 인가 · 만료 안 됐나** 확인
3. **금액을 서버가 다시 계산한다** ← 이게 핵심
   `ticket_products` 의 `meal_fee + agency_fee + wine_min` × `party_size`
   (외화는 `app_config.fx_settings` 의 환율로 — 앱의 `fxTicketCharge()` 와 같은 식)
4. 계산액 ≠ `p_expect_amount` 면 **거부**한다 (앱이 다른 화면을 보고 있었다는 뜻)
5. 잔액이 모자라면 거부
6. 예치금 차감 + `deposit_transactions` 기록 + `tickets` 를 `active` + 계산액으로
7. 전부 성공하거나 전부 없던 일이 된다

> **`p_expect_amount` 를 왜 받나**: 서버가 계산하는데 앱 값을 왜 받는지 —
> **가격이 바뀐 걸 잡기 위해서다.** 회원이 결제창을 열어 둔 사이 어드민이
> 가격을 고쳤으면, 회원이 본 금액과 실제가 다르다. 그냥 서버 값으로 긁으면
> **본 적 없는 금액이 빠져나간다.** 다르면 멈추고 다시 보여줘야 한다.

- 앱: 예치금 결제 자리에서 이 RPC 하나를 부른다 (지금 여러 줄을 대체)
- 되돌리기: 앱을 옛 코드로 (RPC 는 남겨도 무해)
- 확인: 예치금 구매 → 잔액·티켓·거래기록 셋이 다 맞는가 / 취소하면 되돌아오는가

### 3단계 — INSERT 를 잠근다 (위험 낮음 · 1·2단계가 끝나야 가능)

1·2단계가 끝나면 **앱이 회원 세션으로 하는 INSERT 는 「좌석 홀드」 하나뿐**이다.
그러면 이렇게 잠글 수 있다.

```
회원 세션의 tickets INSERT 는
  · status = 'hold'
  · price = 0
  · purchase_id like 'PAYH-%'
  셋을 다 만족해야 한다. 아니면 거부.
```

어드민·`service_role`·SECURITY DEFINER RPC 는 지금처럼 통과. `toss-confirm` 도
service_role 이라 영향 없다.

**이 단계가 끝나면 8번이 닫힌다** — 결제 없이 확정 예약을 만들 방법이 없어진다.

- 되돌리기: `drop trigger` 한 줄
- 확인: 구매(예치금·카드) 둘 다 되는가

### 4단계 — 좌석 홀드도 RPC 로 (선택 · 나중에)

`taam_acquire_seat_hold(p_ticket_id, p_pax)` 로 옮기면 `purchase_id` 형식까지
서버가 정한다. 3단계까지 하면 **실익이 크지 않다** — 홀드는 돈이 안 걸리고
5분이면 사라진다. 다른 일이 없을 때 한다.

## 순서를 지켜야 하는 이유

| 순서를 어기면 | 무슨 일이 나나 |
|---|---|
| 3단계를 먼저 | 동기화 경로가 `active` 를 INSERT 하다 죽는다 → **정상 구매 일부가 조용히 실패** |
| 2단계 없이 3단계 | 예치금 확정은 UPDATE 라 안 막히지만, 금액은 여전히 앱이 정한다 |
| 1단계 없이 3단계 | 위와 같음 — 동기화가 막혀 앱이 에러를 낸다 |

**1 → 2 → 3.** 각 단계 사이에 실제 구매를 한 번씩 해 본다.

---

## 미리 정해야 할 것

### ① 동기화 경로를 정말 없애도 되는가

지금 이 경로가 **실제로 무언가를 메우고 있는지** 먼저 세어 본다.
로컬에만 있고 DB 에 없는 구매가 회원들에게 얼마나 있는지는 서버에서 알 수 없다
(로컬 저장소라서). 대신 **1단계에서 INSERT 대신 알림을 넣어 두면 한 주만에
답이 나온다** — 알림이 안 오면 그 경로는 죽은 코드였다는 뜻이다.

→ **1단계를 「알림만」으로 먼저 넣고, 한 주 보고 나서 INSERT 를 지우는** 것이
   더 안전하다. 이 순서를 권한다.

### ② 서버 금액 계산이 앱과 정확히 같은가

원화는 단순하다(`(meal+agency+wine)×pax`). **외화가 어렵다** —
`fxTicketCharge()` 가 `app_config.fx_settings` 의 환율과 `_fxUnitSum()` 을 쓴다.
서버가 이걸 그대로 옮겨야 하고, **한 원이라도 어긋나면 4번 검증에서 전부 거부된다.**

→ 2단계에 들어가기 전에 **「지금 있는 모든 티켓에 대해 앱 계산 = 서버 계산인가」**
   를 대조하는 조회를 먼저 만든다. 오늘 재구매 가드 때와 같은 순서다.

### ③ 외화 회원이 지금 몇 명인가

없으면 2단계에서 원화만 먼저 하고 외화는 뒤로 미룰 수 있다. 훨씬 빨라진다.

## 예상 규모

| 단계 | SQL | 앱 | 배포 | 위험 |
|---|---|---|---|---|
| 1 (알림만) | — | 작음 | 1회 | 낮음 |
| 1 (INSERT 제거) | — | 작음 | 1회 | 낮음 |
| 2 | 큼 (RPC + 금액 계산) | 중간 | 1회 | **중간 — 금전** |
| 3 | 작음 (트리거) | — | 0회 | 낮음 |
| 4 | 중간 | 중간 | 1회 | 낮음 |

**1·3단계만 해도 8번의 큰 구멍(가짜 확정 예약)은 닫힌다.** 2단계는 금액 위조를
막는 것이라 더 깊지만 더 어렵다. 1 → 3 을 먼저 하고 2 를 따로 잡는 것도
합리적인 선택이다.
