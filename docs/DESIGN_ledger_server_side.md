# 설계 — 예치금 원장(`deposit_transactions`)을 서버로

작성 2026-08-31 · 오늘 한 「구매 흐름 서버 RPC 화」의 연장

## 무엇이 문제인가

```sql
-- deposit_transactions 의 INSERT 정책
(auth.uid() = user_id) OR is_superadmin()
```

회원이 **자기 이름으로 아무 거래기록이나 넣을 수 있다.**

정확히 말하면 **돈은 못 움직인다.** 이 테이블에는 잔액을 바꾸는 트리거가 없다.
그런데 두 가지가 걸린다.

1. **감사 기록이 오염된다.** 2026-08-31 오전에 갇힌 돈 ₩5,000 을 찾을 때 쓴 게
   이 기록이다. 「정상 취소」와 「사고로 돈만 빠진 건」을 구분하는 유일한 근거였다.
   위조된 행이 섞이면 그 판단이 안 선다.

2. **환불 주머니를 바꿀 수 있다.** `_depRefundSplit()` 이 이 기록을 읽어서
   환불을 멤버십/일반 중 어디로 되돌릴지 정한다. 회원이 자기 구매에 대해
   가짜 `ticket_purchase` 행을 넣으면 비율이 바뀐다.
   **금액은 못 늘린다** — 총액은 앱의 환불 계산에서 오고, 이 함수는 나누기만 한다.

## 왜 지금 당장 못 막나

INSERT 를 그냥 막으면 **취소·환불이 깨진다.** 앱이 아직 이 테이블에 직접 쓴다.

| 줄 | 무엇 |
|---|---|
| 16608 | 정원 초과 자동 환불 |
| 19954 | 슈퍼어드민 예치금 부여 |
| 24068 | 티켓 구매 (카드 섞인 경로) |
| 27230 | 취소 — 예치금 환원 |
| 27704 · 27734 | 예치금 반환(멤버십/일반) |
| 37510 · 37522 | 초대 티켓 결제 |
| 23321 | 멤버십 결제 (현재 미사용) |

**9곳이다.** 오늘 오전 사고가 정확히 「금전 경로를 검증 없이 한 번에 바꾼」 것이었다.
같은 실수를 반복하지 않는다.

## 왜 「가드 트리거」로는 안 되나 — 검토했고 버렸다

두 가지를 생각했는데 둘 다 문제를 못 푼다.

* **`balance_after` 를 서버가 덮어쓴다** → 안 된다. 한 구매가 두 주머니에서
  나가면 앱은 **중간값**을 적는다(멤버십 차감 직후 잔액, 그다음 최종 잔액).
  서버가 최종값으로 덮으면 그 의미가 사라진다. `taam_purchase_confirm_deposit`
  도 일부러 중간값을 적는다.

* **`metadata.purchase_id` 가 본인 구매인지 검사한다** → 공격을 못 막는다.
  위조하려는 사람은 **자기 구매**를 참조한다. 소유자 검사는 통과한다.

원장이 위조 불가능해지려면 **서버만 쓰는 수밖에 없다.**

## 설계 — 잔액을 옮기는 함수가 원장도 쓴다

지금 `taam_apply_deposit_delta` 는 잔액만 옮기고, 원장은 앱이 따로 쓴다.
**둘이 갈라져 있는 것 자체가 문제다.** 하나로 묶는다.

```sql
taam_apply_deposit_delta(
  p_user_id  uuid,
  p_mem_delta bigint,
  p_gen_delta bigint,
  p_entries  jsonb default null   -- 🆕 [{deposit_type, change_type, amount, description, metadata}, ...]
)
```

* `p_entries` 가 null 이면 **지금과 완전히 같게** 동작한다 (하위호환).
* 있으면 잔액을 옮긴 뒤 **같은 트랜잭션에서** 원장 행을 쓴다.
* `balance_after` 는 **서버가 계산한다.** 항목을 순서대로 적용하며 누적한다 —
  앱이 적던 중간값과 같은 의미가 되고, 앱이 보낸 값은 쓰지 않는다.
* `user_id` 는 항상 `auth.uid()` (슈퍼어드민이 남에게 부여할 때만 인자 사용).

## 단계

오늘 구매 RPC 를 3단계로 나눠서 안전했다. 같은 방식으로 간다.

**1단계 — 지금 위조된 행이 있는지 센다** (읽기만)
`sql/ledger_audit.sql`. 있으면 규모를 알고 시작하고, 없으면 「지금부터 막는」
문제로 좁혀진다.

**2단계 — 서버 함수에 원장 쓰기를 더한다** (앱은 안 바뀜)
`p_entries` 를 받는 새 시그니처. 이 단계만으로는 **아무것도 달라지지 않는다.**
앱이 안 부르기 때문이다. 되돌리기도 쉽다.

**3단계 — 앱 call site 를 하나씩 옮긴다**
9곳을 **한 번에 바꾸지 않는다.** 한 곳 옮기고 → 배포 → 그 흐름을 실제로 돌려
보고 → 다음. 순서는 위험이 낮은 것부터:

1. 정원 초과 자동 환불 (16608) — 드물게 일어남
2. 초대 티켓 결제 (37510·37522)
3. 취소 — 예치금 환원 (27230)
4. 예치금 반환 (27704·27734)
5. 티켓 구매 (24068)
6. 슈퍼어드민 부여 (19954)

**4단계 — INSERT 정책을 조인다**
9곳이 전부 옮겨진 뒤에만. 그 전에 조이면 안 옮긴 흐름이 죽는다.

```sql
-- 4단계에서 할 것
drop policy deposit_tx_insert_own on public.deposit_transactions;
create policy deposit_tx_insert_server on public.deposit_transactions
  for insert to authenticated
  with check (public._taam_uid_is_super());   -- 회원 직접 INSERT 차단
```

`SECURITY DEFINER` 함수 안에서는 `current_user` 가 소유자라 이 정책에 걸리지
않는다 — 오늘 예치금 가드에서 확인한 것과 같은 성질이다.

## 되돌리기

각 단계가 독립적이다.

* 2단계: `p_entries` 를 안 넘기면 그만. 함수는 옛 시그니처도 유지한다.
* 3단계: 그 call site 만 되돌린다.
* 4단계: 정책 한 줄을 원래대로.

## 2026-09-04 — 원장을 넘기는 결제가 **전부** 막혔다

T등급 회원이 초대 티켓(₩1,400,000)을 결제하지 못했다. 화면에 뜬 말은

```
예치금 차감 실패
column "payment_id" is of type uuid but expression is of type text
```

함수 안의 INSERT 가 `nullif(e->>'payment_id','')` 를 **uuid 컬럼**에 넣고 있었다.

세 가지를 배웠다.

**① 값이 아니라 문장이 문제였다.** plpgsql 은 INSERT 를 처음 실행할 때 한 번
**짜 둔다**. 타입이 안 맞으면 그 자리에서 42804 로 죽는다 — 그 항목에
`payment_id` 가 들어 있든 없든 상관없다. 앱은 이 값을 **한 번도 보낸 적이
없는데** 그래서 죽었다. 「안 보내니까 괜찮다」가 성립하지 않는 종류다.

**② 그래서 조용하지 않고 전부 막혔다.** 원장을 넘기는 call site 는 그때까지
옮겨 둔 것이 전부였고, 그 모두가 같은 문장을 지나간다. 하나가 아니라 전부다.

**③ 앱 폴백은 이걸 못 잡는다 — 그리고 못 잡는 게 맞다.** `_depApplyDelta` 의
폴백은 「함수가 없음(PGRST202)」 하나뿐이다. 여기에 「서버가 터지면 원장 없이
다시」를 더하고 싶어지지만, 그러면 **잔액은 움직이고 원장은 안 써진** 상태로
끝날 수 있다. 이 설계가 없애려던 바로 그 갈라짐이다. 결제를 거절하는 쪽이 낫다.
실제로 이번에도 함수 전체가 롤백돼서 **돈은 1원도 움직이지 않았다.**

### 고친 모양

uuid 모양일 때만 컬럼에 넣고, 아니면 `metadata.payment_ref` 로 남긴다.
무턱대고 `::uuid` 를 붙이지 않은 이유 — 티켓 구매 쪽은 PortOne 결제ID
(`taam-…`)를 `payment_id` 라는 **같은 이름**으로 들고 다닌다. 그 값이 하루라도
섞여 들어오면 이번엔 결제 도중에 터진다. 값은 버리지 않는다.

### 재발 방지

`sql/_test/t_ledger.sh` + `sql/_test/fx_ledger.sql`.
픽스처의 `payment_id` 는 **uuid** 다 — text 로 바꾸면 이 사고가 여기서
재현되지 않는다. 옛 판을 넣고 돌리면 ②번부터 무너지는 것을 확인했다.
